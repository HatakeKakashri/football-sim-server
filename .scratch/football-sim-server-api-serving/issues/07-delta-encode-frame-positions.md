# 07: Delta-encode the frame positions and bring the match under the transfer budget

**What to build:** PRD §10.7 sets a 5 MB transfer budget for a whole match and records that the current render is 6,500,009 gzipped bytes — "the size trigger is already met; the format has not been changed yet, and that decision is recorded rather than silently ignored". Naming players by roster index (ticket 06) is not enough on its own: it takes the match to roughly 6.0 MB, still over the budget. Encode each frame's positions as the delta from the previous frame, so a body carries how far each player moved rather than where they are; the first frame of a segment carries absolute positions, so a segment is still readable on its own. A client reconstructs a position by accumulating the deltas.

Delta encoding is the encoding chosen here because it keeps the 10 Hz frame rate and cuts both the bytes over the wire and the volume the client has to parse — PRD §10.7 already tells the client to parse segment bodies into typed arrays, which is where accumulating a delta belongs. Halving the frame rate would reach the budget too, but it costs the client its animation smoothness, so it is not taken.

**Blocked by:** 06.

**Status:** ready-for-agent

- [ ] A client that accumulates the deltas reconstructs exactly the positions the segment published before the change. This is proved by a test that decodes a rendered body and compares it against the render's own frame positions, for every frame of every segment.
- [ ] The measured gzipped total for m-0001 is at or below the 5,000,000-byte budget, reported by the ignored release size test and by the real-match end-to-end test.
